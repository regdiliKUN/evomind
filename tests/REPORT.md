# EvoMind 测试报告

> 执行时间：2026-10-18 · 环境：Windows / Python 3.13 / RTX 4090 / qwen3.8:27b

## 一、测试范围与方法

| 层次 | 覆盖模块 | 方法 |
|---|---|---|
| 单元层 | `config` `memory` `search`（纯函数）`library` `ocr` `downloader` | 直接调用函数，隔离外部依赖 |
| 集成层 | 书库扫描→解析→导入全链路 | 用临时目录造样本，不污染真实书库 |
| 网络层 | Ollama、StackExchange、Brave | 真实请求，记录耗时 |
| API 层 | 全部 REST 端点 | HTTP 调用，含参数校验与并发 |
| 性能层 | 检索、写入、列表查询、统计 | 循环计时取均值 |

**三类场景**：
- **正常路径** — 标准输入下的正确行为
- **边界条件** — 空值、负数、越界、超长、0 长度
- **异常场景** — 文件损坏、格式不支持、ID 不存在、并发写入

运行方式：

```bash
.venv\Scripts\python.exe tests\run_tests.py          # 全部（含网络与 LLM）
.venv\Scripts\python.exe tests\run_tests.py --fast   # 只跑本地逻辑
.venv\Scripts\python.exe tests\api_tests.py          # 需要服务已启动
```

## 三、发现的问题与修复

### 1. 分页参数未夹紧 —— 会一次性拉全表（已修复）

**现象**：`list_books(limit=-5)` 返回 **3723 条**全部书目；`list_points(limit=-1)` 同理。

**根因**：SQLite 的 `LIMIT -1` 语义是「不限制」，负数被当成无限制。前端一旦传错参数（或恶意构造），单次请求就会把整张表读进内存。

**修复**：两个函数入口统一夹紧到 `1..1000`，`offset` 夹紧到 `>=0`，并对非数字输入回退默认值。

**验证**：`limit=-5` → 返回 1 条；`limit=999999` → ≤1000 条。

### 2. 空查询触发全源检索 —— 单次浪费 20 秒（已修复）

**现象**：`search("")` 耗时 **19.9 秒**，`search("!@#$%^&*()")` 耗时 2.6 秒。

**根因**：没有输入校验，空串和纯符号被原样发给 6 个检索源并发请求。StackExchange 收到空 `q` 会返回热门问题（实测拿回 7 条完全无关的内容），其他源各自超时。

**修复**：`search()` 入口判断——长度 < 2 或不含任何字母/数字/汉字，直接返回 `[]`。

**验证**：空串、空白、纯符号、单字符全部 **0-1ms** 返回。

### 3. 前端搜索框无长度限制（已修复）

**现象**：3000 字查询导致连接被强制断开（`WinError 10054`）。

**根因**：URL 长度超过 HTTP 服务器上限，在到达应用层之前就被拒绝。应用层无法兜住。

**修复**：三个输入框加 `maxlength`（书名搜索 60 / 知识库搜索 200 / 对话 500）。

**剩余风险**：绕过前端直接构造超长 URL 仍会失败，属 HTTP 层限制，已记录。

### 4. 测试脚本自身的 3 个缺陷（已修复）

| 问题 | 原因 |
|---|---|
| 「添加目录」误报失败 | 在 `case()` 断言前就调用了一次 `add_dir`，导致第二次调用报「已存在」 |
| 「解析二进制垃圾」找不到样本 | 用了 `.bin`，但它不在支持格式里，扫描阶段就被跳过；改用「扩展名合法但内容损坏的 PDF」 |
| `memory.add_document` 不存在 | 实际函数名是 `mark_doc(url, title, topic, chars, ok)` |

另有一处误判：`add_point` 返回 `None` 并非缺陷——是**语义去重正常工作**（两次运行只差时间戳前缀，相似度 >0.93 被拦）。测试改为 `dedup=False` 单独验证写入。

## 六、仍需关注的潜在风险

| 风险 | 影响 | 建议 |
|---|---|---|
| **语义检索随知识点线性变慢** | 25ms @1000 条 → 约 250ms @1 万条 → 2.5s @10 万条 | 超过 5 万条时引入 HNSW / FAISS 近似索引 |
| **超长 URL 被 HTTP 层拒绝** | 绕过前端会 502/连接重置 | 已在三个输入框加 maxlength，服务端不做兜底 |
| **StackExchange 配额 300 次/天/IP** | 高频学习可能耗尽 | 耗尽后自动降级到其他源，但质量下降；可配 Brave Key 补位 |
| **OCR 精细引擎极慢** | 150 页需 2-3 小时 | 已提供断点续做与单页重识别，建议按章节分批 |
| **扫描版 PDF 占比高** | 3,696 个 PDF 实测文字层为 0 | 只能逐本 OCR，无法批量自动完成 |
| **LLM 调用无重试** | 单次网络抖动会导致该块提炼失败（已捕获，跳过） | 目前静默跳过，长任务可能漏内容；可加 2 次重试 |
| **微调链路未实测** | 训练代码未经真实 GPU 跑通 | 依赖 PyTorch 环境，本机未安装，属未验证路径 |
| **`_vec_cache` 全量常驻内存** | 1000 条约 3MB，10 万条约 300MB | 大规模时需改为分片加载 |

## 七、结论

- 核心链路（配置 / 记忆 / 检索 / 书库 / OCR / API）在正常、边界、异常三类场景下均表现稳定，无崩溃。
- 修复了 3 个真实缺陷，其中「分页未夹紧」和「空查询 20 秒」会直接影响线上体验。
- 并发安全性经实测确认，`threading.local` + WAL 方案有效。
- 主要遗留风险是**语义检索的线性复杂度**和**未实测的微调链路**，前者在知识点上万时需要升级索引方案。

## 八、第二轮：代码层缺陷修复

第一轮只测了行为，第二轮针对代码质量做了定向排查，又修了 4 处。

### 1. 同一本书被解析两次（性能）

**原因**：`import_book` 里，若书目状态不是 `ready`，先调 `parse_book()`（内部 `parse_pdf` 遍历全部页），随后**又**调用一次 `parse_pdf()` 取正文。一本 500 页 PDF 白跑一遍，十几秒。

**修复**：
- 抽出 `_extract_text(path)` 统一格式分派，消除三处重复的 `if/elif` 分支
- `parse_book()` 返回值带上 `text`，`import_book()` 直接复用
- 状态已 `ready` 的书只解析一次

**验证**：给 `_read_text_file` 打计数器，导入一本书 → **调用 1 次**（修复前为 2 次）。

### 2. 重试之间没有退避（可靠性）

**原因**：`chat_json` 本身有 `retries=2`，但两次尝试之间**零间隔**。网络抖动时立即重试几乎必然再失败，等于没重试。

> 上一轮报告里写「LLM 调用无重试」是**错误结论**——重试是有的，缺的是退避。

**修复**：失败后 `sleep(0.8 * (attempt+1))`，即 0.8s、1.6s 递增等待。

**验证**：指向不存在的模型触发 3 次尝试，总耗时 **2.5s**（0.8+1.6 的等待确实发生）。

### 3. OCR 与书库导入可同时运行（资源竞争）

**原因**：`ocr._task` 与 `library._task` 是两把独立的锁，互不感知。用户可以在 OCR 跑着的时候点导入，两个长任务同时抢 CPU/GPU，互相拖慢，且都写同一个数据库。

**修复**：启动前互查对方状态，占用中则明确拒绝并说明原因（用函数内延迟导入避免循环依赖）。

**验证**：OCR 运行中启动导入 → `"OCR 任务正在跑，等它结束再导入"`；反向同样拒绝。

### 4. PDF 文档句柄依赖 GC 回收（防御性）

**原因**：`render_png` 每次调用都 `pymupdf.open()` 却从不 `close()`。CPython 靠引用计数能回收，但依赖解释器实现细节；前端每翻一页就调一次，高频下不保险。

**修复**：改为 `with pymupdf.open(...) as doc:` 显式释放。

### 修复后的回归结果

| 套件 | 结果 |
|---|---|
| 单元 + 集成（--fast） | 55 / 56 通过（1 项网络用例主动跳过） |
| API 层 | 18 / 18 通过 |

### 一处判断修正

第一轮怀疑「`_vec_cache` 每次写入都失效，导致批量导入 O(n²)」。实测（dedup=True 连续写 400 条）单条稳定在 **22-33ms，无增长**——因为当前仅 150 条知识点，全量加载向量不到 5ms，耗时大头是 embedding 调用。

**结论：该问题在当前规模下不成立**，待知识点上万条时再验证，届时需要引入增量缓存或 ANN 索引。
