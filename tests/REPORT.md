## 一、测试范围与方法

| 层次 | 覆盖模块 | 方法 |
|---|---|---|
| 单元层 | `config` `memory` `search`（纯函数）`library` `ocr` `downloader` | 直接调用函数，隔离外部依赖 |
| 集成层 | 书库扫描→解析→导入全链路 | 临时目录造样本，不污染真实书库 |
| 网络层 | Ollama、StackExchange、Brave | 真实请求，记录耗时 |
| API 层 | 全部 REST 端点 | HTTP 调用，含参数校验与并发 |
| 性能层 | 检索、写入、列表查询、统计 | 循环计时取均值 |

**三类场景**：
- **正常路径** — 标准输入下的正确行为
- **边界条件** — 空值、负数、越界、超长、0 长度
- **异常场景** — 文件损坏、格式不支持、ID 不存在、并发写入

**复现方式**：

```bash
.venv\Scripts\python.exe tests\run_tests.py          # 全部（含网络与 LLM）
.venv\Scripts\python.exe tests\run_tests.py --fast   # 只跑本地逻辑，约 5 秒
.venv\Scripts\python.exe tests\api_tests.py          # 需服务已启动
```

## 三、修复的产品缺陷

### 3.1 分页参数未夹紧 —— 一次请求拉回全表

| | |
|---|---|
| **现象** | `list_books(limit=-5)` 返回 **3,723 条**全部书目；`list_points(limit=-1)` 同理 |
| **根因** | SQLite 的 `LIMIT -1` 语义是「不限制」，负数被当成无限制。前端传错参数或恶意构造，单次请求就会把整张表读进内存 |
| **修复** | 两个函数入口统一夹紧到 `1..1000`，`offset` 夹到 `>=0`，非数字输入回退默认值 |
| **验证** | `limit=-5` → 1 条；`limit=999999` → ≤1000 条 |

### 3.2 空查询触发全源检索 —— 单次浪费 20 秒

| | |
|---|---|
| **现象** | `search("")` 耗时 **19,925 ms**；`search("!@#$%^&*()")` 耗时 2,618 ms |
| **根因** | 无输入校验，空串和纯符号被原样发给 6 个检索源并发请求。StackExchange 收到空 `q` 会返回热门问题（实测拿回 7 条完全无关内容），其他源各自超时 |
| **修复** | `search()` 入口判断：长度 < 2 或不含任何字母/数字/汉字，直接返回 `[]` |
| **验证** | 空串、空白、纯符号、单字符全部 **0-1 ms** 返回 |

### 3.3 前端输入框无长度限制

| | |
|---|---|
| **现象** | 3000 字查询导致连接被强制断开（`WinError 10054`） |
| **根因** | URL 长度超过 HTTP 服务器上限，在到达应用层之前就被拒绝，应用层无法兜住 |
| **修复** | 三个输入框加 `maxlength`（书名搜索 60 / 知识库搜索 200 / 对话 500） |
| **残留** | 绕过前端直接构造超长 URL 仍会失败，属 HTTP 层限制 |

### 3.4 同一本书被解析两次

| | |
|---|---|
| **现象** | 导入一本书时，`parse_pdf` 被调用两次；500 页 PDF 白跑一遍，十几秒 |
| **根因** | `import_book` 中，状态非 `ready` 时先调 `parse_book()`（内部遍历全部页），随后**又**调一次解析函数取正文 |
| **修复** | 抽出 `_extract_text(path)` 统一格式分派（消除三处重复 `if/elif`）；`parse_book()` 返回值带 `text`，`import_book()` 直接复用 |
| **验证** | 给 `_read_text_file` 打计数器，导入一本书 → **调用 1 次**（修复前 2 次） |

### 3.5 重试之间没有退避

| | |
|---|---|
| **现象** | 网络抖动时，`chat_json` 的 2 次重试几乎必然连续失败 |
| **根因** | `retries=2` 存在，但两次尝试**零间隔**。立即重试对网络抖动无效，等于没重试 |
| **修复** | 失败后 `sleep(0.8 * (attempt + 1))`，即 0.8s、1.6s 递增等待 |
| **验证** | 指向不存在的模型触发 3 次尝试，总耗时 **2.5 s**，确认退避发生 |

> **修正第一轮结论**：原文写「LLM 调用无重试」是错的。重试一直有，缺的是退避。

### 3.6 OCR 与书库导入可同时运行

| | |
|---|---|
| **现象** | OCR 跑着时仍可启动导入，两个长任务同时抢 CPU/GPU，互相拖慢，且都写同一个数据库 |
| **根因** | `ocr._task` 与 `library._task` 是两把独立的锁，互不感知 |
| **修复** | 启动前互查对方状态，占用中则明确拒绝并说明原因（函数内延迟导入避免循环依赖） |
| **验证** | OCR 运行中启动导入 → `"OCR 任务正在跑，等它结束再导入"`；反向同样拒绝 |

### 3.7 PDF 句柄未显式释放

| | |
|---|---|
| **现象** | `render_png` 每次调用都 `pymupdf.open()` 却不 `close()` |
| **根因** | CPython 靠引用计数能回收，但依赖解释器实现细节；前端每翻一页就调一次，高频下不保险 |
| **修复** | 改为 `with pymupdf.open(...) as doc:` 显式释放 |
| **性质** | 防御性加固，非已观测到的故障 |

## 四、测试脚本自身的缺陷

这些问题会让**测试结果本身不可信**，一并记录。

| 问题 | 原因 |
|---|---|
| 「添加目录」误报失败 | 在 `case()` 断言前就调用了一次 `add_dir`，第二次调用自然报「已存在」 |
| 「解析二进制垃圾」找不到样本 | 用了 `.bin`，但它不在支持格式里，扫描阶段就被跳过；改用「扩展名合法但内容损坏的 PDF」 |
| `memory.add_document` 不存在 | 实际函数名是 `mark_doc(url, title, topic, chars, ok)` |
| 把去重误判为缺陷 | `add_point` 返回 `None` 是**语义去重正常工作**（两次运行只差时间戳前缀，相似度 >0.93 被拦），测试改用 `dedup=False` 单独验证写入 |

## 六、性能基准

| 操作 | 耗时 | 说明 |
|---|---|---|
| 语义检索（150-1000 知识点） | 25 ms | 全量向量内存比对 |
| 单条知识点写入 | 22-33 ms | 含 bge-m3 embedding |
| 书目列表（300 条） | 2-13 ms | 缓存命中后更快 |
| 书库统计 | 1 ms | |
| 20 并发状态请求 | 284 ms | 全部 200 |
| 24 次混合并发请求 | 169 ms | 全部 200 |
| 扫描 13 万文件 | 11.5 s | IO 密集 |
| OCR 快速引擎 | 3-6 s/页 | 1700×2200 @200dpi |
| OCR 精细引擎 | 40-85 s/页 | 本地视觉模型 |

**并发结论**：`threading.local()` + WAL 在 6 线程并发写入下无异常，20 并发读全部正常，未出现 `SQLITE_BUSY`。

**批量写入无平方增长**：`dedup=True` 连写 400 条，单条稳定 22-33 ms。原因是当前规模下全量加载向量 <5 ms，耗时大头是 embedding 调用。

> **修正第一轮结论**：原文怀疑 `_vec_cache` 每次写入失效会导致 O(n²)。实测否定——该问题在当前规模（150-1000 条）下不成立。

## 八、结论

1. **核心链路稳定**。配置、记忆、检索、书库、OCR、API 在正常、边界、异常三类场景下均未崩溃，61 项单元 + 18 项 API 用例全通过。
2. **并发方案有效**。`threading.local()` + WAL 经 6 线程并发写入与 20 并发读验证，无锁冲突。
3. **两处性能缺陷影响明显**。空查询 20 秒、重复解析整本书，都是用户能直接感知的浪费，已修复。
4. **测试本身也需要被测试**。第一轮的 3 个失败全部源于测试脚本，说明「测试失败」不等于「产品有缺陷」，必须先排除测试自身的错误。
5. **两个未验证区域需要正视**：微调链路（一行没跑过）和万条以上知识点的检索性能（未触达）。前者是功能空白，后者是规模天花板。
