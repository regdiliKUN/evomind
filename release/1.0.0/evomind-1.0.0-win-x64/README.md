# EvoMind · 自进化学习引擎

> 开发验证：`python -m unittest discover -s tests -p "test_*.py"`、`python tests/run_tests.py --fast`、`node --test tests/frontend_tests.cjs`。快速验证使用临时数据；详见[本轮优化与测量说明](tests/OPTIMIZATION.md)。

## 2026-10-21 学习升级

- **知识二次炼化**：知识库点「一键炼化全部书籍」，自动遍历全部已入库的书籍知识，按书籍分批处理，无需选方向、不受120条限制。完成进度会持久保存，再次点击自动跳过已完成且未变化的内容。也可用「仅炼化当前范围」处理所选方向最近120条。保留原始知识、引用及分页历史，支持停止后继续。
- **随机方向**：自主进化页填一个预设领域（默认 ZBrush），点「刷新方向」获得6个候选，或点「随机选一个方向」自动填写。随机选择不启动学习；选好3/6/10/16轮后，再点「开始进化学习」。ZBrush 内置30个具体主题，其余领域使用通用学习维度组合。
- **一键清理重复知识**：知识库点击「一键清理重复项」，合并同方向、结论及补充内容一致的重复条目，保留较高可信度的代表条目和其他来源。归档记录可通过「撤销上次清理」恢复，原引用仍可打开；相似但不同的内容不会按向量分数自动删除。
- **搜索质量**：通用搜索与专用来源并行；ZBrush、Blender 增加官方文档目录直连。处理搜索跳转链接和跟踪参数，优先相关文档，限制同域结果占位。长文按相关段落提炼，知识必须提供原文依据并通过模型证据核对。
- **连续学习**：间隔可设1–30秒，从上一轮结束计时；新配置默认15秒，旧20分钟配置升级为30秒。导入、OCR、微调和炼化期间等待。点击学习「停止」同时关闭持续调度；关闭持续开关只停止后续调度，当前学习可正常收尾。
- **运行稳定性**：学习、炼化、书库、OCR和微调共用任务准入保护，避免重复点击和后台线程尚未启动时的并发冲突；任务启动失败会释放占位。书库扫描改为后台运行。

使用方式和实测范围见 [学习升级说明](LEARNING_UPGRADE.md)。

## 2026-10-22 学习方向自动更换

「自主进化」页底部新增 **学习方向自动更换**：只填一个模糊领域（如「光固化 3D 打印」），系统自己跑完全程。

1. **拆解**：按母方向生成若干具体子方向（默认 6 个），每条都要求可检索、可验证。模型不可用时用本地候选池按母方向拼装兜底，一定落在范围内。
2. **连续学**：当前子方向连续学 N 轮（默认 100 轮，超过引擎单批上限时自动分批）。
3. **自动换**：满 N 轮后从剩余子方向里随机挑下一个；换向前校验候选是否仍在母方向语义范围内，越界的丢弃重选；最近 3 个方向不重复。
4. **不中断**：子方向用尽时先补充新的合法子方向，补不出来才回收已学过的；最后还有本地拼装的兜底方向。
5. **可停可续**：暂停会让当前这一轮跑完再停，恢复后从剩余轮次接着学；不想学某个方向可以「跳过当前方向」，立刻换下一个。进度、当前方向、切换历史全部落库，重启后仍可查看。
6. **汇总**：达到总轮次上限（默认 300）或手动结束时，输出各方向的轮次、新增知识条数和代表结论；越界丢弃的方向单独计数，不计入成果。也可用 `?format=text` 直接取纯文本。

参数（每方向轮数、总轮次上限、子方向数量、不重复窗口、边界校验开关）在面板里直接改，也会写回配置。逐轮优化记录见 [ITERATION_LOG.md](ITERATION_LOG.md) 与 [ITERATION_LOG_2.md](ITERATION_LOG_2.md)。

使用方式和实测范围见 [学习升级说明](LEARNING_UPGRADE.md)。

## 2026-10-23 多模态摄取

改造前它只认 `text/html`：图片、音频、视频、PDF 在抓取阶段被判「非文本内容」直接丢掉，检索阶段还会主动过滤 `.pdf/.png/.jpg`。

现在补上四条通道，全部落成**文本 + 模态标签**，再走原有的提炼 → 证据核对 → 去重入库：

| 内容 | 通道 |
|---|---|
| 图片 | 本地视觉模型描述画面 + 转录图中文字（失败退 RapidOCR） |
| 音频 | faster-whisper 本地转写，带时间戳 |
| 视频 | 平台字幕优先（vtt/json3/ttml）→ 无字幕转写音轨 → 可选抽帧 |
| PDF | PyMuPDF 文本层 → 扫描件逐页 OCR |

配套改动：

1. **检索**：新增 Wikimedia Commons / Openverse / Internet Archive / YouTube（yt-dlp）四个免 Key 媒体源。
2. **节奏**：每轮媒体默认最多 2 个、媒体检索隔轮执行——不让一段音频转写把一轮学习拖长十倍。
3. **降级**：缺视觉模型/ASR/yt-dlp/PyMuPDF 只影响对应能力，界面「多模态」页的能力卡直接显示缺什么、怎么补。
4. **问答**：`/api/chat` 支持附图，图片先转文字再进 RAG 上下文（主模型不需要视觉能力）。
5. **来源可追溯**：知识条目的 `source_kind` 会标 `image` / `audio` / `video` / `pdf`。
6. **查缺补漏**：给已经学过的方向补媒体——先让模型指出「文字讲不清、只能看图/看演示」的缺口，
   再检索图片/视频/音频并提炼入库；已读过的来源自动跳过，可以反复点，越补越深。
   书名类方向（「书库 · 书名 (作者)」）会自动清洗成可检索的主题。

实测（4090 / qwen3.8:27b）：图片解析 11-15 秒、arXiv PDF 15 页 0.5 秒、19 分钟 YouTube 视频取中文字幕 2.8 秒、
2 小时音频转写 42 秒、图片全链路入库 26 秒 3 条知识、单方向补漏 2 分 53 秒新增 9 条视频知识。

评估过程、关键改动点与预期效果见 [多模态评估与改造](MULTIMODAL.md)。

## 它解决什么问题

大多数「本地 AI」是静态的：模型训练完就固定了，你不知道它懂什么、不懂什么，也没法让它变强。

EvoMind 把它反过来：**你只给一个方向，剩下的它自己干**。它知道自己缺什么，会主动去补，补完存下来，攒够了再把知识压进模型权重。

## 三层进化

| 层 | 做什么 | 见效 |
|---|---|---|
| **知识层（RAG）** | 自主检索 → 抓正文 → LLM 提炼知识点 → 语义去重入库 | 几分钟 |
| **权重层（LoRA）** | 知识库导出 → 扩写成问答对 → LoRA 微调 → 合并权重 | 几小时 GPU |
| **资源层** | 识别 HF 模型/数据集 → 判断相关性 → 预算内自主下载 | 学习时顺带 |

## 为什么它不会原地打转

普通爬虫是「搜关键词 → 存起来」，搜完就没了。

EvoMind 每轮都会把 **「已掌握的知识」+「已用过的检索式」** 一起喂回模型，强制它计算新的知识空白。所以：

```
第 1 轮  →  建立全景框架和核心概念
第 3 轮  →  进入机制原理与量化细节
第 6 轮  →  挖边界条件、工程实践、争议点
```

反思阶段产出的「下一步该深挖什么」会直接变成下一轮的最高优先级缺口。

## 实测效果

一次真实运行（RTX 4090 / qwen3.8:27b）：

```
方向：RAG 系统的检索质量优化与重排序
3 轮 / 93 秒 → 31 条知识，24 篇资料
```

学到的内容是这种粒度的：

> 在医疗程序重排序任务中，经过 ListNet 微调的 109M 参数 Cross-Encoder 在 NDCG@3 上比 4B 参数 LLM 重排序器高 2.6 个百分点。

问它「小型 Cross-Encoder 和大型 LLM 该选哪个」，它会分场景回答并标注 `[1][2][3]` 引用；问到没学过的内容，它直接说「我目前学到的还不够回答这部分」，**不编**。

## 本地书库（手动导入）

网上抓不到的内容，用这个补——你自己的电子书、PDF、笔记，导入后走同一套提炼入库流程。

### 支持的格式

| 类型 | 格式 | 说明 |
|---|---|---|
| 纯文本 | `.txt` `.md` `.csv` | 自动探测编码（UTF-8 / GBK / Shift-JIS 等） |
| 电子书 | `.epub` `.pdf` `.docx` `.rtf` | EPUB 按章节解析，PDF 提取文字层 |
| 网页存档 | `.htm` `.html` | trafilatura 提取正文 |
| 链接 | http/https | 网页直接提炼；PDF/EPUB 直链会先下载再解析 |

**不处理**：图片、音视频、压缩包、`.doc`（需先转 `.docx`）、`.xls`。

### 扫描版 PDF 的真相

PDF 分两种：**有文字层**（能提取）和**扫描图**（提取不到字）。系统会自动检测——每页少于 40 字就判定为扫描版，标记为「已跳过」并说明原因，**不会浪费时间去解析**。

如果你发现大部分 PDF 都被跳过了，那是因为它们是扫描件——**扫描件可以 OCR**，见下一节。

## 扫描件 OCR（图像识别取字）

扫描版 PDF 和图片里的文字，可以识别成可学习的语料。

### 双引擎，按需选

| 引擎 | 速度 | 特点 | 适合 |
|---|---|---|---|
| **快速** RapidOCR | GPU 约 0.2-0.5 秒/页 · CPU 约 2-5 秒/页 | 纯文字识别，不懂版面 | 中文 / 英文印刷体、批量跑 |
| **精细** 本地视觉模型 | 约 40-85 秒/页 | 能理解表格、标题层级、图注 | 日文、表格、复杂排版 |

同一页日文技术书的实测对比：

```
快速引擎：483 字 / 6.0 秒   →  「夕个么一卜」「の動·の動·」大量乱码
精细引擎：897 字 / 85.4 秒  →  「タイムシートの読み方」完整段落，层级清晰
```

字数几乎翻倍，而且精细引擎输出的是能读懂的完整句子。**日文和表格页一定要用精细引擎。**
系统会在识别完成后检查平均每页字数，低于 150 字就提示换引擎。

### GPU 加速（装了显卡一定要开）

默认装的是 **CPU 版** onnxruntime，识别只吃 CPU，显卡基本闲着（实测占用 5%）。
换成 GPU 版后检测、方向分类、文字识别三段全部走 CUDA：

```bat
.venv\Scripts\pip uninstall -y onnxruntime
.venv\Scripts\pip install onnxruntime-gpu==1.22.0
```

**不用另装 CUDA Toolkit**：项目里装了 torch(cu124)，它自带 cudart/cublas/cudnn9，
`backend/ocr.py` 启动时会把 `torch/lib` 加进 DLL 搜索路径，ORT 直接就能用。

版本要对得上：`onnxruntime-gpu` 1.23+ 要 CUDA 13，1.22 及以下才吃 CUDA 12（对应 torch cu124）。

实测（319 页中文扫描书《传奇 Zbrush 数字雕刻大师之路》，同样 41 页样本）：

| 配置 | 吞吐 | 提升 | 显存 |
|---|---|---|---|
| CPU 1 线程（默认旧行为） | 24 页/分钟 | — | 0 |
| GPU 2 线程 | 124 页/分钟 | **5.1×** | 12 GB |
| GPU 3 线程（默认） | 170 页/分钟 | **7.0×** | 16 GB |
| GPU 6 线程 | 183 页/分钟 | 7.6× | 18 GB |

除了换后端，还做了两件事把 GPU 喂满：

- **渲染与识别流水线化**：单独一个线程提前把 PDF 页渲染进队列（渲染在 CPU、识别在 GPU），
  不再「渲染 150ms → 等识别 → 再渲染」串行空转。
- **多线程并发识别**：GPU 推理时 CPU 在切图/预处理，几页交错才能让显卡持续有活干。
  线程数按显存自动选（≥20GB 显存开 3，否则 2），也能在设置里用 `ocr_workers` 手动指定。

抽屉右上角会显示 `GPU · 3 线程` 或 `CPU · 1 线程`，一眼能看出识别到底跑在哪。
没有 NVIDIA 显卡、或者 CUDA 库不全时，程序会自动退回 CPU，不会报错。

### 怎么用

书库里找扫描版的书（状态「已跳过」），点旁边的 **OCR** 按钮：

1. **选页范围** — 填 `1-50` 或 `all`。建议先跑 5-10 页看质量
2. **选引擎** — 先试快速，字太少或乱码多就换精细
3. **开始识别** — 后台逐页跑，实时显示进度和耗时
4. **校对** — 点任意页，右边同时显示原图和识别文本，直接改，点「保存校对」
5. **导入知识库** — 走和其他书一样的提炼流程

### 几个实用细节

**断点续做**：识别过的页自动跳过。跑到一半停了，下次接着跑不重复耗时。

**单页重识别**：觉得某页不好，选中它点「换引擎重识别」，只重跑这一页。

**原图对照**：左边原图、右边文本。图片实时从 PDF 渲染，不额外占磁盘。

**校对标记**：改过的页在列表里显示 `✓`。

**识别完自动转可导入**：状态从「已跳过」变「可导入」，章节按每 10 页一组切好。

**批量跑也能盯着看**：勾选多本点「OCR 选中」后，书库页会出现进度条，显示 `第几本/共几本 · 总体百分比 · 当前书第几页`，点旁边的「查看」打开抽屉，它会自动跟着当前正在识别的那本书走——原图、识别文字、页码列表都是实时的，换书时自动切过去。中途刷新页面，进度会自动接回来。

**卡住会自己恢复**：识别线程如果异常退出，不会再让「开始识别」一直点不动（5 分钟没翻页就自动释放锁）。

### 时间成本要有预期

一本 150 页的扫描书：快速约 15 分钟，精细约 2-3 小时。

建议**先挑最需要的章节跑**（比如 `1-40`），而不是整本。3,696 个 PDF 全跑一遍不现实。

### 多目录配置

可以添加任意多个目录，每个目录独立设置排除关键词：

```
目录 A: K:\书籍\我的电子书库    排除: 成人
目录 B: D:\技术文档             排除: 临时,备份
目录 C: E:\论文库               排除: (无)
```

排除规则是**路径子串匹配**——只要路径里含这些词就跳过。用来避开不适合进知识库的目录。

### 触发方式

控制台「书库」页：

1. **扫描目录** — 只登记书目清单，不解析内容。12 万文件约 12 秒
2. **勾选书目 → 导入选中** — 才真正解析、提炼、入库
3. **粘贴链接 → 从链接导入** — 单篇网页或电子书直链

扫描和导入分开是有意的：先让你看清有什么，再决定导哪些，避免误导入几万本没用的。

### 导入后的组织与索引

```
library_dirs   →  目录配置（路径、排除规则、上次扫描时间）
    ↓
books          →  书目（格式、字数、页数、状态、知识点数、所属方向）
    ↓
book_chapters  →  章节（序号、标题、字数、该章产出知识点数）
    ↓
knowledge      →  知识点（带 book_id 可回溯到书）
```

知识点和其他来源共用同一个 `knowledge` 表，所以：

- 问答时书里的内容和网上学的混在一起检索
- 每条知识点都带 `《书名》 章节名` 作为出处
- 按 `book_id` 可以查某本书贡献了哪些知识，删除书时可一并清除

**单本上限**：默认每本书最多提炼 40 个块（约 8 万字）。一本 500 页的书不会跑一整天。可在导入时调整。

### 状态说明

| 状态 | 含义 |
|---|---|
| 待解析 | 已登记，还没解析 |
| 可导入 | 解析成功，有正文 |
| 已导入 | 已完成提炼入库 |
| 已跳过 | 扫描版 / 正文过少 / 格式不支持（会写明原因） |
| 失败 | 文件损坏或权限问题 |

## 检索源与质量

检索质量直接决定学不学得到东西。实测结论：

| 源 | 需要 Key | 质量 | 说明 |
|---|---|---|---|
| **StackExchange** | 否 | ★★★★ | 建模 / 3D 打印方向的主力源，走开放 API 拿问答正文 |
| **Brave Search** | 是（免费 2000 次/月） | ★★★★★ | 通用搜索，填了明显更准 |
| GitHub | 否 | ★★★ | 代码仓库 |
| arXiv | 否 | ★★★★ | **仅学术方向启用** |
| Wikipedia | 否 | ★★ | 概念性内容 |
| 官方文档目录 | 否 | ★★★★ | ZBrush、Blender 直接从官方目录按主题检索 |
| Bing / DuckDuckGo | 否 | 依网络而定 | 与专用源并行，空结果时不会阻断官方目录检索 |

两个关键设计：

**短查询与多语言补充。** 优先使用3–8个英文关键词，保留软件名和具体操作，并补充官方站点查询及中文实践查询。历史查询和下一步知识缺口会跨学习任务保留。

**arXiv 按方向启用。** `mesh`、`generation` 这类词在学术语境和 DCC 语境下完全是两回事——不设这道闸门，「ZBrush 面数取舍」会搜回一堆 `3D Mesh Generation` 论文。

## 什么方向学得到，什么学不到

这是使用时最容易踩的坑。**方向必须拆到「有文字资料」的粒度**。

✅ 学得到：

```
角色雕刻的拓扑与细分策略：ZBrush 与 Blender 的重拓扑工作流、
四边面布线与形变需求、细分层级与细节承载的关系
```

❌ 学不到：

```
ZBrush 面数取舍 + 光固化 0.05mm 细节保留 + 网格水密化 + 抽壳壁厚
```

后者把「建模」和「打印工艺」两个领域的知识硬拼在一起，而它们**交叉部分几乎没有文字资料**——视频教程里才有，系统抓不到。

正确做法是**拆成两个方向分别跑**：建模归建模，打印工艺归打印工艺。

## 自主下载的四道闸门

它确实有权限自己下载东西，但**不可能把硬盘塞爆**：

1. **单体积上限** — 默认 40GB，超过直接跳过
2. **总预算** — 默认 200GB，累加超过就停
3. **磁盘余量** — 下载前检查剩余空间，不足 1.15 倍就跳过
4. **相关性筛选** — 先让模型判断「这东西对当前方向有没有用」，没用不下

下载的 GGUF 会自动 `ollama create` 注册，可在设置里直接切换使用。

## 配置

所有参数在网页「设置」页改，写进 `data/config.json`，**无需重启**。

几个值得调的：

| 参数 | 默认 | 说明 |
|---|---|---|
| `queries_per_round` | 4 | 每轮生成几个检索式 |
| `fetch_per_round` | 8 | 每轮读几篇 |
| `min_relevance` | 0.45 | 知识点入库门槛，调到 0.6 只收强相关 |
| `dedup_threshold` | 0.93 | 语义去重阈值，调到 0.88 更宽容 |
| `idle_seconds` | 15 | 持续自学的空闲间隔，范围1–30秒；旧分钟配置自动迁移 |
| `rotation_rounds_per_direction` | 100 | 方向轮换：每个子方向连续学多少轮（1–2000） |
| `rotation_total_rounds` | 300 | 方向轮换：总轮次上限（1–100000） |
| `rotation_subdirection_count` | 6 | 方向轮换：首次拆出多少个子方向（2–20） |
| `rotation_recent_window` | 3 | 方向轮换：最近多少个方向内不重复选中（1–20） |
| `rotation_boundary_check` | true | 方向轮换：换向前校验语义边界 |
| `rotation_replenish` | true | 方向轮换：子方向用尽时自动补充 |
| `rotation_max_failures` | 2 | 方向轮换：连续几批没推进就暂停（1–10） |
| `disk_budget_gb` | 200 | 资源总预算 |

## 数据备份与恢复

设置页「数据备份与恢复」，一键把整个学习数据打成 zip：

| 内容 | 说明 |
|---|---|
| `knowledge.db` | 在线一致性快照（引擎正在写也能导）：知识点 / 书 / 章节 / OCR 结果 |
| `config.json` | 当前配置，密钥类字段打码 |
| `manifest.json` | 备份时间与各表行数 |
| `README.txt` | 手动恢复步骤（新机器 / 新实例兜底） |

- 备份存在 `data/backups/`，最多保留最近 **10** 份，超量自动删最旧的；
- 下载后另存到别处（移动硬盘 / 网盘），**换机器、重装、误删数据/ 都靠它救回来**；
- 恢复会先用备份里的库覆盖当前库，**覆盖前自动把当前库另存一份**（备注 `pre-restore`），全程可回退；
- 学习 / 导入 / OCR / 持续自学进行中会拒绝恢复，防止把正在写入的库换掉；
- 备份里的数据库会先过 SQLite 完整性校验，坏包直接拒收。

## 权重层（微调）

控制台「权重进化」页，四步：

1. 装微调环境（约 3GB：PyTorch + Transformers + PEFT）
2. 知识库攒够几百条
3. 生成训练集（自动把陈述改写成自然提问）
4. 开始微调

默认走 **bf16 LoRA + gradient checkpointing**，不依赖 bitsandbytes（Windows 上更稳）。

### 基座模型怎么选

| 基座 | 显存 | 训练耗时 | 用途 |
|---|---|---|---|
| `Qwen/Qwen2.5-7B-Instruct`（默认） | 约 17GB | 197 条 1 轮 **121 秒** | 真能得到有用的模型 |
| `Qwen/Qwen2.5-0.5B-Instruct` | 约 2GB | 几十秒 | 只想快速验证链路通不通 |

设置页可改。7B 在 RTX 4090（24GB）上实测跑通：LoRA 可训练参数 4037 万，占全模型 **0.53%**，首次需下载 14GB。0.5B 训出来能力很弱，别指望能用，它只适合确认链路。

> 已有安装的 `data/config.json` 里存的值优先于默认值，改默认不影响老配置。

### 训练集质量是成败关键

早期版本的训练集有个致命问题：问句直接拼 `topic`，而 topic 常常是「书库 · 某本书名」，于是变成——

```
Q: 请说明「书库 · FGOミステリー」领域中的这个要点：在FGO设定中，修复特异点…
A: 在FGO设定中，修复特异点的主要动机之一是回收圣杯碎片…
```

问题问的是「这本书是什么领域」，答案却在讲特异点设定，**完全对不上**。这样训出来的模型只会复读。

现在改成用模型逐条改写问句：

```
Q: FGO里修复特异点除了救世，还有什么实际好处？
A: 在FGO设定中，修复特异点的主要动机之一是回收圣杯碎片以作为卡勒迪亚的魔力资源…
```

改写很慢（27B 模型每条约 5-6 秒，200 条要 15-20 分钟），但**这一步不能省**。

### 训练只学「怎么答」

`labels` 会把 prompt 段（system + 用户问题）全部 mask 成 `-100`，只对 assistant 的回答计算 loss。否则模型会把容量浪费在学习「复读问题」上。

### 微调真正有效的前提（实测结论）

链路是通的，但**样本量不够时微调等于没做**。实测数据：

```
197 条样本 · 1 轮 · 24 steps · loss 2.20 → 2.04 · 训练 121 秒
```

训完拿同一个模型去问训练集里的问题：

| 问题 | 训练集答案 | 微调后的回答 |
|---|---|---|
| ZBrush 64 位最低内存 | **16GB**（32 位 8GB） | 「64 位最低 8GB，32 位 4GB」❌ 答反了 |
| FGO 修复特异点的好处 | 回收圣杯碎片作魔力资源 | 「获得大量材料和经验」❌ 游戏常识幻觉 |

**24 步不足以改变 7B 模型的权重分布。** 这个量级的训练连「记住几条事实」都做不到。

要有实际效果，至少需要：

- **1000+ 条样本**（当前 197 条）
- **3-5 轮**（当前 1 轮），对应 500-1000 steps
- 学习率可尝试提到 2e-4

所以现实的做法是：**先把知识层（RAG）用起来**，它即时生效、可增删、可溯源。等知识库自然积累到几千条，再考虑微调固化。这也是为什么系统设计成两层——不是每个阶段都需要动权重。

> 样本质量决定成败。建议先去知识库删掉明显没用的内容再训。

## 已知限制

- **只在 Windows 上测过**，其他平台理论上可用但未验证
- **桌面图标仅 Windows 有效**（走 `.lnk` + `WScript.Shell`），其他系统安装器会自动跳过
- 免费检索源**有速率限制**；Brave 可配置 API Key，网络受限时也可设置代理
- 「0 条新知识」可能来自抓取失败、相关性不足、证据核对未通过或重复，不能据此判断方向已学透
- 模型的证据核对有助于减少误读，仍不能替代人工核实；来源本身的版本冲突需回到原文判断
- 微调不是越大越好，几百条样本容易过拟合，建议小步多次
